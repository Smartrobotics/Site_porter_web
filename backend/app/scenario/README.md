# scenario_gen — генерация сценариев без правок робота («путь 0»)

## Зачем

Робот принимает **только имя** сценария: `/scenario_name` — это `std_msgs/String`,
а движок читает `<scenario_dir>/<имя>.json`. Параметров он не принимает вообще.
Всё зашито внутри JSON: `marker_id`, `map_no`, `path_no`, координаты, этажи лифта.

Сервер стоит на том же роботе, поэтому он может подставить значения сам, положить
готовый файл рядом с остальными сценариями и опубликовать его имя.
**Правок в C++ не требуется, воркспейс не пересобирается.**

Движок читает файл заново на каждый запуск (`load_json` в
`run_scenario_on_demand`, кэша нет), поэтому свежесозданный сценарий
подхватывается сразу.

## Что параметризовано

Шаблон `template_roundtrip.json` получен из рабочего `press_scenario_4.json`
заменой **шести** значений. Остальные шаги не тронуты.

| Параметр | Шаг | Смысл |
|---|---|---|
| `pickup_path_no` | 4 | `path_no` места на 2F, где стоит нужная платформа |
| `pickup_marker` | 6 | её маркер |
| `dropoff_path_no` | 26 | `path_no` места выгрузки на 1F |
| `return_pickup_path_no` | 32 | `path_no` места, откуда забираем порожнюю |
| `return_marker` | 34 | маркер порожней платформы |
| `return_dropoff_path_no` | 57 | `path_no` места на 2F, куда ставим порожнюю |

Четыре из них (6, 26, 32, 34) — те, которыми `press_scenario_4` отличается от
`press_scenario_5`, то есть уже менялись на роботе.

Шаги 4 и 57 в обоих готовых сценариях равны `path_no=1`: рейс возвращает
платформу на то же место 2F, откуда забрал. Как параметры они добавлены, чтобы
источник и назначение на 2F можно было задавать раздельно — **на роботе это
сочетание ещё не проверялось.**

**Проверка эквивалентности** — генератор воспроизводит оба готовых сценария
без единого расхождения:

| Параметры | Результат |
|---|---|
| `marker 4, path 1 → 1F path 3`, вернуть `marker 5` с `path 4` на `path 1` | `press_scenario_4.json` |
| `marker 5, path 1 → 1F path 4`, вернуть `marker 4` с `path 3` на `path 1` | `press_scenario_5.json` |

Значит поведение робота не меняется, меняются только эти шесть чисел.

## Использование

```python
from gen_scenario import generate
name = generate(pickup_marker=4, pickup_path_no=1, dropoff_path_no=3,
                return_pickup_path_no=4, return_marker=5,
                return_dropoff_path_no=1)
# опубликовать name в /scenario_name
```

```bash
python3 gen_scenario.py --pickup-marker 4 --pickup-path 1 --dropoff-path 3 \
                        --return-pickup-path 4 --return-marker 5 \
                        --return-dropoff-path 1
python3 gen_scenario.py ... --dry-run     # показать JSON, не записывая
```

Имя по умолчанию — `run_<timestamp>`. Запись атомарная (временный файл +
`os.replace`): движок может читать каталог в тот же момент, и недописанный
файл сломал бы разбор JSON.

`cleanup()` удаляет старые `run_*.json`. Файлы без этого префикса не трогаются
никогда — они лежат в git.

## Проверка

```bash
python3 selftest.py        # ничего не пишет в каталог робота
```

Шесть групп проверок. Главная — первая: генератор с параметрами
`press_scenario_4` и `press_scenario_5` должен выдавать эти файлы **без
единого расхождения**. Если она проходит, поведение робота не изменится.

Остальное: подстановка каждого из шести параметров в свой шаг, отказ при
неполном наборе, запись файла и валидность JSON, `cleanup` не трогает файлы
из git, в каталоге робота не осталось мусора.

Код возврата `0` — всё прошло, `1` — есть ошибки. Проверено, что тест не
«всегда зелёный»: если убрать плейсхолдер из шаблона, первая группа падает.

### Проверка вручную

```bash
# посмотреть JSON, ничего не записывая
python3 gen_scenario.py --pickup-marker 4 --pickup-path 1 --dropoff-path 3 \
    --return-pickup-path 4 --return-marker 5 --return-dropoff-path 1 --dry-run

# записать во временный каталог, а не к роботу
python3 gen_scenario.py ... --scenario-dir /tmp/scen --name run_test
```

### На роботе

Сгенерировать с параметрами `4 1 3 / 4 5 1` и сравнить с `press_scenario_4`:
файлы должны совпасть. Затем запустить и убедиться, что робот едет так же,
как по исходному сценарию.

Первый прогон с **разными** `pickup_path_no` и `return_dropoff_path_no`
делать под присмотром: это единственное сочетание, которое на роботе ещё
не проверялось.

## Границы

Сценарий остаётся **полным рейсом туда-обратно** (65 шагов): доставка 2F→1F и
возврат порожней 1F→2F одним запуском. В рабочем процессе это описано как два
отдельных сценария, но разделение на роботе ещё не проверялось, поэтому здесь
сохранена та форма, которая работает.

Что **не** параметризовано и требует замеров на объекте, если появятся новые
места: `map_no`, координаты `set_robot_position` после смены этажа, `path_no`
подъезда к лифту, этажи в `elv_call_floor`. Подставлять их наугад нельзя —
робот поедет не туда.

## Фрагменты — рейс из отдельных сценариев

Движок держит **очередь** `/scenario_name` и выполняет имена по одному
(`ScenarioEngine::loop`). Поэтому рейс можно собирать из коротких сценариев,
публикуя следующий после завершения предыдущего. Тогда решение «возвращать
порожнюю или нет» принимается **после `put_down`**, а не при старте — как и
задумано в `docs/siteporter-db.ja.md` §11.

Шесть шаблонов в `fragments/` (по `docs/SitePorterScenario/`), константы
объекта в `floors.json`, схема цепочек — `docs/SitePorterScenario/scenario.drawio`.

| Фрагмент | Параметры |
|---|---|
| `init` | этаж HOME (карта + координаты из `floors.json`) |
| `pick_up` | `map_no`, `path_no`, `marker_id` |
| `move_to_target`, `return_home` | `map_no`, `path_no` |
| `elv` | этажи откуда/куда; подъезд, offset, позиция после выхода — из `floors.json` |
| `put_down` | — |

```python
from gen_scenario import plan_deliver, plan_collect, plan_go_home, generate_chain

plan = plan_deliver({'floor': 2, 'path_no': 1, 'marker_id': 4},
                    {'floor': 1, 'path_no': 3}, go_home=False)   # до put_down
names = generate_chain(plan, run_id='1756280412')
# → run_1756280412_01_init, _02_pick_up, _03_move_to_target, _04_elv, _05_move_to_target, _06_put_down
# публиковать по одному; после put_down сервер решает:
tail = plan_collect(porozhnyaya, kuda, from_home=False)   # приклеить возврат
tail = plan_go_home(1)                                     # или ехать домой
```

```bash
python3 gen_chain.py deliver_collect --pickup 2:1:4 --dropoff 1:3 \
        --collect-pickup 1:4:5 --collect-dropoff 2:1 --dry-run   # план и шаги
python3 gen_chain.py deliver --pickup 2:1:4 --dropoff 1:3        # записать фрагменты
```

Имя фрагмента `run_<run_id>_<NN>_<kind>` — по `robot_state.scenario_name`
видно, какой рейс и на каком шаге стоит робот.

**Два правила.** Упавший сценарий *не очищает* очередь движка — поэтому
фрагменты публикуются строго по одному, никогда не класть в очередь всю
цепочку. `init` делает `set_robot_position` в HOME — только первым
фрагментом цепочки, стартующей из HOME; хвост `collect` после доставки идёт
с `from_home=False`.

**Прогон на роботе — `run_chain.py`.** Публикует фрагменты по одному и ждёт
`/scenario_state` (`scenario_control/ScenarioState`, задача `R-1`). Нужен
запущенный `scenario_control_json` и `source devel/setup.bash`.

```bash
# с паузой перед каждым фрагментом — для первого раза
python3 run_chain.py deliver_collect --pickup 2:1:4 --dropoff 1:3 \
        --collect-pickup 1:4:5 --collect-dropoff 2:1 --step

# развилка сервера руками: до put_down, потом хвост возврата
python3 run_chain.py deliver --pickup 2:1:4 --dropoff 1:3 --no-home
python3 run_chain.py collect --pickup 1:4:5 --dropoff 2:1 --no-init
```

На `FAILURE`/`CANCELED` останавливается и печатает: причину, шаг, есть ли
платформа на вилах, размер очереди движка (должен быть 0). Следующий
фрагмент никогда не уходит без `SUCCESS` предыдущего. Результат
сопоставляется по `scenario_name` — latched-состояние от прошлого рейса
не засчитывается.

Класс `ChainRunner` (`run_fragment(kind, params, run_id, seq)` →
терминальный `ScenarioState`) — ядро цикла сервера: после `put_down`
сервер смотрит в БД и решает, `plan_collect(from_home=False)` или
`plan_go_home()`.

**Отличия от монолита.** Склейка `deliver_collect` совпадает с
`press_scenario_4` во всём, кроме двух решений по `scenario.drawio`: проезд
вперёд после лифта в обе стороны (в монолите — только на 2F) и нет захода в
холл (route 3) на 2F перед подъездом к адресу. Селфтест §9 фиксирует именно
это. На роботе не проверялось — при первом прогоне смотреть на эти два места.
Рейс в пределах одного этажа не поддержан (`NotImplementedError`).

## Дальше

Это временное решение под срок. Правильное — отдельный топик, куда сервер
шлёт JSON с параметрами, а движок подставляет их сам (`run()` уже принимает
готовый JSON, менять выполнение шагов не нужно). Тогда обмен через файловую
систему исчезнет. Порядка 50 строк в `scenario_engine.cpp`; существующий
`/scenario_name` при этом остаётся нетронутым.
